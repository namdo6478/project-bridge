# 실제 저장 단계 데이터 모델

이 문서는 현재 화면 예시를 실제 회원과 데이터 저장 기능으로 바꾸기 위한 공급자 중립 계약입니다. 데이터베이스나 인증 서비스가 바뀌어도 화면과 업무 규칙이 흔들리지 않도록 먼저 엔터티와 권한을 고정합니다.

## 핵심 엔터티

| 엔터티 | 역할 | 주요 제약 |
| --- | --- | --- |
| 사용자 | 로그인 주체, 역할과 계정 상태 | 이메일·휴대폰은 비공개, 탈퇴는 즉시 물리 삭제하지 않음 |
| 판매자 프로필 | 장터에 노출되는 이름·지역·사업자 정보 | 연락처 공개 범위를 사용자별로 적용 |
| 매물 | 장비 기본 정보와 판매 상태 | 작성자 또는 관리자만 변경, 삭제는 복구 가능한 소프트 삭제 |
| 매물 사진 | 원본 파일과 노출 순서 | 매물마다 대표 사진 1장, 파일 키는 공개 URL과 분리 |
| 관심 매물 | 사용자와 매물의 저장 관계 | `(user_id, listing_id)` 중복 금지 |
| 문의·메시지 | 구매자와 판매자의 대화 | 해당 구매자·판매자만 조회, 차단 후 새 메시지 금지 |
| 신고 | 허위·사기 의심 신고와 운영 상태 | 신고자·관리자만 원문 조회, 처리 이력 보존 |
| 상태 이력·감사 로그 | 판매 상태와 관리자 조치 기록 | 일반 사용자가 수정·삭제할 수 없음 |

## 권한 기준

| 작업 | 비회원 | 인증 회원 | 매물 소유자 | 관리자 |
| --- | --- | --- | --- | --- |
| 승인된 매물 검색·상세 | 가능 | 가능 | 가능 | 가능 |
| 관심 매물·문의 | 불가 | 휴대폰 인증 후 가능 | 자기 매물 문의 불가 | 운영 확인 가능 |
| 매물 등록 | 불가 | 휴대폰 인증 후 가능 | 가능 | 운영 목적으로 가능 |
| 매물 수정·삭제·상태 변경 | 불가 | 불가 | 가능 | 가능 |
| 연락처 원문 조회 | 불가 | 공개 조건 충족 시 | 본인 정보만 | 분쟁 처리 시 가능 |
| 신고 검수·제재 | 불가 | 불가 | 불가 | 가능 |

## 반드시 지킬 보안 규칙

1. 화면에서 보이지 않는다고 보호된 것이 아니므로 모든 쓰기 작업은 서버에서 로그인·소유권·역할을 다시 확인합니다.
2. 휴대폰·이메일 원문은 검색용 공개 데이터와 분리하고 로그에 남기지 않습니다.
3. 사진 업로드는 MIME, 확장자, 용량, 픽셀 크기를 검사하고 임의 파일명을 사용합니다.
4. 삭제 요청은 우선 소프트 삭제하고 신고·분쟁 보존 기간이 지난 뒤 별도 작업으로 물리 삭제합니다.
5. 관리자 조치와 판매 상태 변경은 감사 로그를 남기고 일반 사용자가 수정할 수 없게 합니다.
6. 공개 목록은 `approved`이면서 삭제되지 않은 매물만 반환합니다.

## 구현 순서

1. Supabase 프로젝트 생성과 환경변수 연결
2. 준비된 마이그레이션으로 사용자·프로필·매물·사진·문의·신고 테이블과 RLS 적용
3. 매물·사진 저장, 소유권 검사, 임시 저장 복구
4. 관심 매물과 문의 저장
5. 신고·관리자 권한·감사 로그 연결
6. 백업, 보존 기간, 탈퇴·삭제 작업 자동화

코드 계약은 `lib/types/marketplace.ts`, 저장소 경계는 `lib/data/marketplace-repository.ts`, 공통 권한 함수는 `lib/data/authorization.ts`에 있습니다.

초기 PostgreSQL/Supabase 스키마는 `supabase/migrations`에 준비되어 있습니다. 버킷은 비공개로 두고 승인된 매물 사진만 정책으로 읽게 하며, 업로드 경로는 `{user_id}/{listing_id}/{file}` 형식을 사용합니다.
